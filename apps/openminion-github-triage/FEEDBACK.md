# OpenMinion 0.1.24 SDK Feedback

1. **Direct decorator calls vs registry calls:** Calling a `@tool`-decorated Python function directly behaves differently depending on whether a dict or its generated Pydantic argument model is passed, whereas `derive_tool_specs(decl.tool_family_spec())` plus `ToolRegistry.execute_calls([ProviderToolCall(...)])` is deterministic and returns structured verification metadata. A short official runnable snippet showing `@tool` through `ToolRegistry.execute_calls` and `result.content` JSON decoding would save builders significant trial and error.
2. **Session initialization bookkeeping events:** `SQLiteSessionStore.create_session()` automatically logs an initial `agent.bound` event inside `session_events`. Builders reading `event_count` for billing, analytics, or progress indicators need explicit documentation to filter by `event_type` rather than assuming one row per user action.
3. **Nested internal import paths for `TaskState` and diagnostics:** `TaskState` (`openminion.modules.brain.loop.recursive.schemas`) and `PhaseStatus` / `phase_status_payload` (`openminion.modules.brain.diagnostics.status`) are clean typed models, but are not re-exported at top level in `openminion.__init__`. Exporting stable diagnostics and task-state contracts from a public SDK namespace would prevent fragile deep module imports.
4. **Reasoning model empty-content safety:** OpenAI-compatible reasoning endpoints can exhaust short `max_tokens` budgets (`160`) before emitting final answer text or wrap output in `<think>...</think>` tags. Setting `max_tokens=512` and rejecting empty cleaned content prevents silent blank notes.
